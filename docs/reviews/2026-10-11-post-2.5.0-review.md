## Bugs found

1. **Check mode pointed at the entry being replaced** (#129). `WriteService.check` (`src/hivemind/services/write.py:96`) looked up `related` while the `supersedes` targets were still active. As a result, `hive_write(..., supersedes=[A], check=true)` usually listed A as the nearest entry, and the tool text says to withdraw over such an entry. A real write never lists A, because A is already superseded by then. Reproduced with a unit test that fails on main.
2. **Blank notes: Postgres and memory disagreed** (#131). Postgres's `\S` (`pgstore.py` `BATCH_FEEDBACK_SIGNALS`, `HEALTH_SCALARS`) counts U+00A0 and U+0085 as characters; `memstore.py` `str.strip` does not. So on Postgres, a `helpful` report with a note of only a no-break space set `last_confirmed_at`, and a stale report produced an empty `correction`. Reproduced on both adapters. Fixed by trimming notes when they are stored.
3. **Two definitions of "this source only cites an entry"** (#131). `write_warnings.py:40` and `domain/health.py:16` used different patterns. A `…/entries/<id>` URL got the `no_primary_source` warning but still counted as grounded in the fleet health metric. Now there is one pattern, and a Postgres test checks that both regex engines agree.
4. **Not fixed, low (possible, not reproduced):** pin "flagged since pin" compares `pinned_at` from the database clock (`INSERT_PIN ... now()`, `pgstore.py:185`) with feedback `updated_at` from the app clock (`services/feedback.py`). If a pod runs ahead of the database, a re-pin may not clear `flagged`. The fix would be to pass `pinned_at` from the service clock.

The rest came out clean: visibility of `similar`, `supersedes`, `correction`, `related` and pins; at most two store calls in flight per search; explore and version grouping keep chain order and are stable across pages; REST and MCP payloads match; migrations 0014/0015 and their rollbacks; fleet health SQL against MemoryStore.

## Skills and always-on text

The `hivemind` skill (9,740 B after #128) is in good shape after the #107 rewrite. It reads as one loop (catch up, recall, write, rate) and has little duplication. #128 freed 373 B with no change in behaviour: shorter wording for the `hive_write` supersede/related/see_also rule, the `hive_register` name rule and the `hive_feedback` batch sentence; the skill drops a clause the tool description already states.

**Approved 2026-10-11 and opened as #132 (stacked on #128):** in skill §3, replace "Search with your draft summary first and act on the nearest entry (the same for `related` in the write reply; withdraw yours if it duplicated one)" with "Before writing, call `hive_write` with `check: true` and act on its `related` and `warnings`". Check mode embeds the full draft, not just its summary. It reports the warnings before anything is stored, and it removes the write, withdraw, rewrite churn the current flow causes. It is about the same length.

## MCP tool text (the maintainer's question)

- **Descriptions:** after #128 they total about 6.2 KB for ten tools. What remains is guidance the #107 rewrite deliberately moved out of the skill: the importance rubric, the body template per kind, the foreign-fleet rule, and the evidence fields on hits. Cutting it would remove guidance, not noise, and moving it back to the skill saves nothing, since both count toward one budget.
- **Schemas:** these were the real bloat, and nothing budgeted them. pydantic repeats each argument name as a `title` and spells every optional argument as `anyOf [T, null]` with `default: null`. #130 strips both from `tools/list`: input schemas go from 5,872 to 2,695 B, and the whole payload from 13,990 to 10,466 B, about 10.1 KB once #128 lands too. The server still validates calls with its own model, so clients that send `null` keep working. An opus review found no problems after the fix for a latent `title`-named-argument bug.

## Refactoring opportunities (not done; small payoff)

- `services/search.py:311` and `:337`: with version grouping and explore both on, a search reads `pairwise_similarity` twice, the second time over a superset of the first. One read would do.
- `services/pins.py:24`: the flagged check reads up to 50 feedback rows per pin. `BATCH_FEEDBACK_SIGNALS` already computes `newest_flag_at`; exposing it on `FeedbackSignals` would remove that read and the caveat about 50 newer notes burying a flag.
- `pgstore.py:336` and `:349`: `BATCH_FEEDBACK` and `BATCH_FEEDBACK_SIGNALS` duplicate the counting SQL; `quality_counts` could become a wrapper over `feedback_signals`.
- `memstore.py:107` and `:242`: two loops that compute all-pairs cosine.
