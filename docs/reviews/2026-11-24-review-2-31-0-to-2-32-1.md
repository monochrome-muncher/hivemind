# Review of the changes from 2.31.0 to 2.32.1 (2026-11-24)

- **Range:** `v2.31.0..v2.32.1` (`f2a633d..586ccb8`), PRs #482 to #507: 98 files, about 4,700 lines added.
- **Asked for:** bugs, security, performance, readability, and docs and test gaps over the whole range, weighting the code merged after the 2026-11-23 security audit (baseline `6226951`, clean).
- **Weighted most:** the portal fleet activity chart (#504, ADR 0165) and its log scale toggle (#506), the OpenCode and KiloCode single system message fix (#503), the Docker push retry (#495).
- **Read lighter:** the client package fixes (#482 to #484, #486, #490, #493), which the 2026-11-19 client packages review and the 2026-11-23 audit already covered; the docs drift PRs (#487, #488, #496 to #499) and the badges (#500, #502); the release PRs.
- **Checks:** `make check` clean and the unit suite green on the fix branch. Postgres was not running in this container, so the store contract ran in CI on each PR.
- Line numbers point into `586ccb8` (v2.32.1).

## Result

No security issue and no correctness bug. The new route applies the same visibility rule as every other read, on both sides of the query, and the chart sets every label as text. What turned up is documentation drift in ADR 0165, a cache key that could fall out of step with `Visibility` later, and two filters that never match.

## Security

- **Who may call it.** `GET /v1/portal/fleet-activity` refuses anything but an agent key (`api/routes/portal.py:312`). It is on the portal proxy allowlist as a GET only (`portal/app.py:64-65`). The admin panel cannot reach it.
- **What it counts.** Both sides of the query carry the caller's visibility clause on the entry (`store/pgstore/metrics.py:103-118`, `:612-623`). The memory store applies `entry_is_visible` to writes and to the rated entry (`memstore/metrics.py:415-447`). A level 0 key gets nothing without a store call (`services/fleet_activity.py:58-61`). Ratings use the same rule as the activity view: no set-aside rows and no revoked raters (`_RATING_COUNTS`, `sql_common.py:52-65`; `_live_feedback`, `memstore/state.py:77-87`). The contract tests cover visibility, heirs, level 3, set-aside verdicts and revoked raters in both adapters (`tests/integration/test_store_contract.py`).
- **What it reveals.** Member names and per-day counts of their writes and ratings, only on memories the key can read. ADR 0165 §3 records that ratings counts reach the portal, which ADRs 0080 and 0090 had kept for the admin. The person decided that; it is not re-raised.
- **The per-key cache.** The key was `(name, level, home fleet, inherited, days, date)` (`services/fleet_activity.py:23`, `:62-69`). Those are all the fields `visibility_clause` reads today, so no key could read another key's report. Listing the fields by hand means a field added to `Visibility` later would be left out of the key. [#508](https://github.com/monochrome-muncher/hivemind/pull/508) uses the frozen, hashable `Visibility` itself.
- **The front end.** `fleetchart.js` builds every node through `h()` and `svg()`, which set text with `textContent` (`portal/static/fleetchart.js:4-5`). Agent names never reach `innerHTML`. A 401 signs out through `guarded` (`portal/static/session.js:31-43`), so the card cannot hang in "loading" after a rejected key.
- **Docker push retry (#495).** The retry step runs only when the first push failed (`.github/workflows/docker-publish.yml:109`, `:119-131`). Cosign signs the digest of whichever push succeeded (`:144`). No new secret or permission.
- **OpenCode (#503).** The reminder text is unchanged. It is only placed differently (`plugins/hivemind/opencode/hivemind.js:105-118`).

## Bugs

None found. Checked in detail:

- **The window.** `window_start` is UTC midnight of the first day and `until = since + days` (`services/fleet_activity.py:57`, `:73`). The zero-filled day list covers the same days, so no store row falls outside it. The one-day window test pins today only.
- **The cache.** A read that races with `invalidate()` is not cached (the generation check, `:72`, `:77`). A failed read is never cached. The size bound is FIFO, not LRU (`:78-80`). That is fine under a TTL.
- **The chart.** The window toggle drops a late answer through the token (`fleetchart.js:205-215`). The log scale keeps zero on the axis and ticks powers of ten, and the tests run the shipped module under Node. The "Other agents" line sums the agents left out per day (`:39-43`).
- **The OpenCode fix.** The v1 hook appends to the last string. The v2 hook replaces the last text part with a copy (`opencode/hivemind.js:114-118`). If the last part is not text, v2 still pushes a second part. OpenCode and KiloCode put text there today, so that is an edge, not a bug.
- **The Docker retry.** It also retries a real build failure, which costs a 60 s wait and a second failing build before the job fails. That is acceptable for a release job.

## Performance

- **Ratings scan.** No index serves `feedbacks` by rater and time, so the ratings side is a sequential scan of `feedbacks` (`store/pgstore/metrics.py:109-114`). ADR 0165 §5 measured 33 ms for 30 days at 500,000 rows. The person chose not to add a migration. The cache holds one answer per key, window and `HIVEMIND_METRICS_ENTRY_COUNTS_TTL` (300 s by default, not the 30 s the ADR said; fixed in #509).
- **Windows the UI never asks for.** The route accepts `days` from 1 to 90 (`api/routes/portal.py:306`), so one key can ask for up to 90 uncached scans per TTL, where the UI asks for 7 and 30 only. It needs an authenticated agent key, each scan is bounded and the cache holds at most 256 answers. No action. The Thursday perf check can watch the query once `feedbacks` grows, and the index in ADR 0165 §5 is the fix if it is ever slow.
- **No single flight.** Concurrent misses for the same key both run the query (`services/fleet_activity.py:70-75`). The cache is per key, so a lock shared by all keys would serialise unrelated readers. No action.

## Readability

- The hand-listed cache key and two filters that never match (`services/fleet_activity.py:102`, `memstore/metrics.py:444`). The port says quiet days have no row, and both adapters emit a row only after counting something. Fixed in #508, which also removes the unit test that pinned the dead filter with a zero row no adapter can produce.
- The rest of the new code is short and plain: one service, one SQL statement with a comment on why it has no index, and one chart module with named constants. No change suggested.

## Docs and tests

- **ADR 0165 drift** (fixed in #509): it said the TTL defaults to 30 s (it is 300 s, `config.py:292`); it gave the port as `fleet_activity(fleet_id, since, visibility)` (`until` is missing, `ports/metrics.py:42`); and it ended §2 with "it holds no state, so there is no cache and no wiring", which contradicts its own cache paragraph and `services/wiring.py:57-70`.
- **Runbook** (fixed in #509): the `HIVEMIND_METRICS_ENTRY_COUNTS_TTL` row did not say that the admin activity view and the portal chart cache by it.
- SPEC §5.1 (`SPEC.md:200`), the CHANGELOG rows for 2.32.0 and 2.32.1, AGENTS.md and the `portal.js` module map already describe the chart. No gap found.
- Tests: the route, the service cache, both adapters and the chart's pure functions are covered. The DOM wiring of the toggles has no test, as for the other portal cards.

## Not re-raised

The client packages' findings from the 2026-11-19 review (all merged), the 2026-11-23 audit, and the owner's decisions recorded in ADR 0165 (ratings visible to members, no new storage, no index).
